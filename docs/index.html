LLVM-Whitebox

Making LLVM optimization passes and the IR changes they cause visible, on demand.

What it is

You hand the tool a source file and the compiler flags you would normally use. It gives you five panels: your source, the final assembly, the ordered list of the optimization passes that ran on a function you pick — with the ones that actually changed the IR highlighted — and, for whichever pass you click, a side-by-side diff of the IR before and after it.

The questions it is built to answer are "why didn't that optimization fire?" and "which pass broke this?".

There are two programs. pass-diff is a C++ CLI built directly on LLVM's PassInstrumentationCallbacks API; it is the part that observes passes and produces IR. UI.py is a PySide6 desktop app that drives clang, drives pass-diff, and renders the result. Each is usable without the other — pass-diff is a perfectly good standalone tool.

Relation to Compiler Explorer

Compiler Explorer is the tool people reach for to explore compiler behaviour interactively: paste a snippet, switch compilers and versions, see the output immediately. It is built for playing around, and it is good at it.

This project is aimed at a different job — debugging the compilation of an actual application, with its real flags, where what you need is a specific answer about a specific pass rather than a broad survey. Two concrete consequences follow from that difference in purpose.

IR is produced lazily. Nothing dumps IR at every pass up front. list-passes compares before/after snapshots only to decide whether each pass changed anything, and discards the text. The IR for a diff is generated only for the one pass you clicked. That is what keeps a long compilation workable: finding one diff does not require writing out hundreds of megabytes of dumps first.

Whole projects are the target. The intended end state is pointing the tool at a real project's build and investigating one file or one function across the entire compilation. Tracking file and function identity through the pipeline is the bulk of that work and is not implemented. Today the tool handles one translation unit at a time.

Status

Prototype. One C++ translation unit, desktop UI. It works end to end and the pass/IR data it reports is faithful to a real compile (see the fidelity problem), but there is no project-level build integration and no source-line ↔ IR mapping. Results are kept in an output folder, so reopening an earlier run, or clicking a pass a second time, costs nothing.

Build

cd pass-diff
cmake -S . -B build -DLLVM_DIR=<llvm prefix>/lib/cmake/llvm
cmake --build build
# optional: cmake --install build --prefix $HOME/.local

The build adapts to the LLVM it finds: it links the single shared libLLVM if that LLVM was built that way (typical for distribution packages), otherwise the individual component libraries; it adds -fno-rtti if LLVM was built without RTTI; it rejects LLVM older than 18; and it builds pass-diff as Release by default.

Python environment

python3 -m venv ui/.venv          # in the repository root
ui/.venv/bin/pip install -r ui/requirements.txt

UI_run.sh activates $VENV if set, else ui/.venv if it exists, else nothing.

Which clang: the one of pass-diff's LLVM

clang and pass-diff must come from the same LLVM, or the pipeline string and the .ll may not parse. So only pass-diff is chosen, and clang follows from it. CMake records the LLVM version and its tools folder (LLVM_TOOLS_BINARY_DIR) in the binary, pass-diff toolchain-info prints them, and the UI takes clang++ and llvm-cxxfilt from that folder. Which pass-diff: --pass-diff PATH, else (with --cache) the one of that run, else pass-diff on PATH, else pass-diff/build/pass-diff.

Release vs Debug LLVM

With several LLVMs, build one folder per LLVM (e.g. build and build-debug) and pick with --pass-diff. A release clang's C++ frontend is about 37× faster than a debug one (~28 s → ~1 s on a coroutine-heavy C++20 file). A debug build gives you LLVM's assertions and the verify passes in the pipeline; a release clang drops those (it passes -disable-llvm-verifier), so its pipeline shows one VerifierPass fewer.

Gotcha

If CMake complains about a mismatched cache directory — which happens after the repository or a build folder is moved — reconfigure with cmake --fresh -S . -B build -DLLVM_DIR=.... The CMake cache stores absolute paths.

Quick start

# build the C++ tool (see INSTALL.md for LLVM_DIR)
cd pass-diff
cmake -S . -B build -DLLVM_DIR=/usr/lib/llvm-18/lib/cmake/llvm
cmake --build build

# Python environment, in the repository root
cd .. && python3 -m venv ui/.venv && ui/.venv/bin/pip install -r ui/requirements.txt

# launch the UI on the bundled sample
ui/UI_run.sh

With no arguments the UI opens test/src/hello_world.cpp. Pick a function in the dropdown above the pass list; passes that changed its IR have a blue background. Click one to compute and show its diff. The terminal prints which pass-diff and clang are used and the output folder the results went to.

UI command line

UI_run.sh activates the Python environment and forwards every argument to UI.py. The argument list is split at the first bare --: everything before it belongs to the tool, everything after it is handed to clang untouched. All examples run from the repository root.

ui/UI_run.sh [--code FILE] [--output DIR | --cache DIR] [--no-overwrite]
              [--pass-diff PATH] [--verbose] [-- CLANG_FLAGS...]
FlagMeaning
--code FILE Source file to analyze. C++ only. Defaults to test/src/hello_world.cpp relative to UI.py.
--output DIR Output folder for this run, created if missing. Defaults to tmp/<file>_<YYYY-MM-DD_HH-MM-SS>. See output folders.
--cache DIR Reopen the output folder of an earlier run: its last used source version, with its last used flags and pass-diff unless new ones are given. Cannot be combined with --code or --output (exit code 2).
--no-overwrite A changed source or changed settings get a new src-N / cfg-N folder instead of overwriting the last used one.
--pass-diff PATH The pass-diff binary to use; clang++ and llvm-cxxfilt come from the LLVM it was built against. Default: with --cache the one of that run, else pass-diff on PATH, else pass-diff/build/pass-diff.
--verbose Print every clang and pass-diff command before running it.
-- ... Everything after this goes to clang++ verbatim, and transitively determines the pass pipeline that gets replayed.

Examples

# bundled sample, clang defaults
ui/UI_run.sh

# a specific file at -O3
ui/UI_run.sh --code test/src/hello_world.cpp -- -O3

# compare what changes between optimization levels: run twice
ui/UI_run.sh --code test/src/hello_world.cpp -- -O1
ui/UI_run.sh --code test/src/hello_world.cpp -- -O3

# target-specific cost models reach the passes through the IR
ui/UI_run.sh --code mycode.cpp -- -O3 -march=znver3

# forward a backend knob, as you would to clang
ui/UI_run.sh --code mycode.cpp -- -O3 -mllvm -unroll-threshold=1000

# AT&T instead of the default Intel assembly syntax
ui/UI_run.sh --code mycode.cpp -- -O3 -masm=att

# use another LLVM, e.g. a debug build
ui/UI_run.sh --code mycode.cpp --pass-diff pass-diff/build-debug/pass-diff -- -O3

# reopen an earlier run without recompiling
ui/UI_run.sh --cache tmp/hello_world_<timestamp>
Note

The flags after -- are used for all three clang invocations — the starting IR, the assembly, and the pipeline query — so every panel in the window describes the same compile. Changing them changes which passes exist at all, which is usually the point.

On top of your flags the UI adds a few that do not change the compile: -fno-discard-value-names for the IR (a release clang would otherwise print %0 instead of %a.addr), -masm=intel for the assembly, placed before your flags so a -masm=att of yours wins (non-x86 targets ignore it), and -Wno-unused-command-line-argument for the two calls on the .ll.

Output folders & cache

Every run writes its results into an output folder. Nothing is written next to the source file.

tmp/<file>_<YYYY-MM-DD_HH-MM-SS>/   (default; or --output DIR)
  session.json          original source path, last used src-N / cfg-N
  src-N/                one per version of the source
    <file>.cpp          copy of that version — this copy is what gets compiled
    source.json         sha256 of the content
    cfg-N/              one per settings (compiler flags + pass-diff)
      config.json       flags, pass-diff path and LLVM version, clang path and version
      <file>.ll  <file>.s  pipeline.txt  passes.txt
      diffs/fK_rN.txt   show-diff output, saved on the first click
  • Reuse. A cfg-N holding the .ll, .s, pipeline.txt and passes.txt is complete: the UI loads it and calls neither clang nor pass-diff. passes.txt is written last, so a run that crashed half way is not mistaken for a complete one.
  • Diff cache. The first click on a pass saves show-diff's raw output to diffs/fK_rN.txt (K: the function's position in the dropdown, N: the run's position in its list); later clicks, also in later sessions, read it. Numbers instead of names because mangled names can exceed the 255-byte file name limit.
  • Includes. The copy is compiled with -iquote <folder of the original>, so #include "x.h" next to the original still resolves. Headers are not copied, so they are not versioned.
  • Overwriting (default). Rerunning into the same folder with a changed source overwrites the last used src-N (and deletes its cfg-*); changed flags or pass-diff (path or LLVM version) overwrite the last used cfg-N.
  • --no-overwrite. Changes get a new src-N / cfg-N instead, so earlier versions stay.
  • Either way, an existing src-N with the same content or cfg-N with the same settings is reused, e.g. after undoing an edit.

--cache DIR needs no --code: it reopens the last used src-N of DIR — the copy, even if the original has changed since. Flags and pass-diff come from the last used cfg-N, each unless given: flags after -- or --pass-diff select the matching cfg-N, computing it if it does not exist.

Old output folders

Folders written before --pass-diff existed have no pass_diff in their config.json. --cache stops with a warning for them; start a new run with --code.

pass-diff command line

pass-diff takes LLVM IR (.ll), not C++. It has two subcommands for that, plus toolchain-info.

pass-diff list-passes <input.ll> [--pipeline <spec>] [--mllvm <opt>]...
pass-diff show-diff   <input.ll> <Function> <N> [--pipeline <spec>] [--mllvm <opt>]...
pass-diff toolchain-info
ArgumentMeaning
list-passes Runs the pipeline and prints one tab-separated line per pass run, in execution order: <Function>\t<Pass>\tdid changes|did no changes. Module passes are reported under <Globals>.
show-diff Runs the pipeline and prints the IR before and after one run.
toolchain-info Prints llvm-version <version> and tools-dir <folder>: the LLVM pass-diff was built against and that LLVM's tools folder, where the UI takes clang++ from.
<Function> A function name exactly as in the first column of list-passes (mangled), or <Globals>.
<N> 1-based position of the run in that function's list, i.e. among the list-passes lines with that first column.
--pipeline <spec> Any string PassBuilder::parsePassPipeline accepts. Defaults to default<O3>. For fidelity, pass clang's own printed pipeline.
--mllvm <opt> Forward one LLVM backend option, as clang's -mllvm does. Repeatable.

Examples

# get IR to work on, with no passes applied yet
clang++ -O3 -Xclang -disable-llvm-passes -S -emit-llvm hello_world.cpp -o hw.ll

# which passes ran, and which did something
pass-diff list-passes hw.ll

# only the ones that changed the IR
pass-diff list-passes hw.ll | grep 'did changes$'

# the runs on add(int, int), numbered as show-diff numbers them
pass-diff list-passes hw.ll | grep -P '^_Z3addii\t' | cat -n

# inspect the 4th run on add(int, int)
pass-diff show-diff hw.ll _Z3addii 4

# a module pass
pass-diff show-diff hw.ll '<Globals>' 4

# a different optimization level
pass-diff list-passes hw.ll --pipeline 'default<O1>'

# a hand-built pipeline, to isolate one transform
pass-diff show-diff hw.ll _Z3addii 1 --pipeline 'function(sroa)'

# replay clang's real pipeline (what the UI does)
PIPE=$(clang++ -O3 -Wno-unused-command-line-argument -mllvm -print-pipeline-passes -S hw.ll -o /dev/null)
pass-diff list-passes hw.ll --pipeline "$PIPE"
Quoting

Real pipeline strings are several kilobytes of <, >, ;, ( and ). Always quote them. This is also why UI.py builds an argv list and never uses shell=True — a shell would read those characters as redirections and subshells.

Worked example

Start from the bundled sample, which has an add function whose parameters clang initially spills to stack slots:

int add(int a, int b) { return a + b; }

Emit the pre-optimization IR and list the passes:

$ clang++ -O3 -fno-discard-value-names -Xclang -disable-llvm-passes -S -emit-llvm \
      test/src/hello_world.cpp -o hw.ll

$ pass-diff list-passes hw.ll
# Executed Passes and if they changed IR (pipeline: default<O3>)
<Globals>  MemProfRemoveInfo          did no changes
<Globals>  Annotation2MetadataPass    did no changes
<Globals>  ForceFunctionAttrsPass     did no changes
<Globals>  InferFunctionAttrsPass     did changes
<Globals>  CoroEarlyPass              did no changes
_Z3addii   EntryExitInstrumenterPass  did no changes
_Z3addii   LowerExpectIntrinsicPass   did no changes

(Tabs shown as columns.) That is 347 runs for this three-function file — 32 on <Globals> and 105 on each function — which is a decent illustration of why dumping IR for all of them up front is the wrong default.

Function: _Z3addii
======================================================

--- IR BEFORE ---

  %a.addr = alloca i32, align 4
  %b.addr = alloca i32, align 4
  store i32 %a, ptr %a.addr, align 4, !tbaa !5
  store i32 %b, ptr %b.addr, align 4, !tbaa !5
  %0 = load i32, ptr %a.addr, align 4, !tbaa !5
  %1 = load i32, ptr %b.addr, align 4, !tbaa !5

The two allocas and four memory operations are gone. In the UI this is: pick add(int, int) in the function dropdown, click the 4th entry, SROAPass.

Architecture & data flow

The first launch for a source and settings makes three clang calls and one pass-diff call; the first click on each pass makes one more pass-diff call. Every result is written to the output folder (the file names on the right below), and a later launch or click that finds it there makes no call at all. Only the first clang call parses the C++ source, which is almost all of clang's runtime; the assembly and the pipeline query start from its .ll and take well under a second.

  src-N/source.cpp (copy) + user flags (after `--`)
         │
         ▼
  clang++ -S -emit-llvm -Xclang -disable-llvm-passes
  (the only call that runs the C++ frontend)
         │
         ▼
     cfg-N/source.ll  pre-optimization IR
         │
         ├─────────────────────────────┬──────────────────────────────┐

The consequential property of this shape: every diff costs a full pipeline run. pass-diff is stateless between invocations, so show-diff re-runs the whole pipeline from the starting IR and snapshots only the watched run. That is the trade being made — no up-front cost and only the diffs you looked at are stored, but the first click on a pass has the latency of one optimization pipeline. The diff cache makes every later click free; for a large project, where one pipeline run takes long, the first click will still hurt.

The fidelity problem

This is the core design concern of the project, so it is worth stating plainly. A tool that shows you passes is useless — actively misleading — if the passes it shows are not the passes your build actually runs. There are three independent ways to get this wrong, and each is handled deliberately.

1. Don't reconstruct the pipeline, ask for it

The naive approach is to map -O2 to default<O2> and call it a day. That silently diverges, because clang builds its pipeline with the real TargetMachine and a PipelineTuningOptions derived from every flag on the command line. So instead:

clang++ <your flags> -mllvm -print-pipeline-passes -S file.ll -o /dev/null

The printed string is fully parameterized — unroll thresholds, simplifycfg options, coro passes — and it round-trips through PassBuilder::parsePassPipeline, so pass-diff replays it verbatim. This has to be its own clang invocation: -print-pipeline-passes suppresses real codegen, so the .s comes out empty and it cannot be folded into the assembly call.

2. Don't start from -O0 IR

The starting IR is produced with the user's real flags plus -Xclang -disable-llvm-passes, which stops the pipeline and changes nothing else. Forcing -O0 instead would be wrong twice over: it tags every function optnone, which makes optimizer passes skip them entirely, and it changes CodeGen-level decisions — adds noinline, keeps "frame-pointer"="all", drops TBAA metadata. The result would be IR that no real compile ever produces.

3. Give the passes a real cost model

If PassBuilder gets TM = nullptr, then PassRegistry.def falls back to a bare TargetIRAnalysis() — a generic, target-agnostic cost model. Every pass that asks "how wide is a vector register?" or "what does this instruction cost?" — the loop vectorizer, the SLP vectorizer, the unroller, the inliner — then makes different decisions than your backend does. pass-diff therefore builds a real TargetMachine, and takes its target description from the IR rather than from its own command line. See TargetMachine construction for why that indirection is the useful part.

What is still approximate

A handful of passes read global cl::opt state rather than pipeline parameters, and the pipeline string cannot capture those. clang's -mllvm sets exactly those globals, so the UI scrapes -mllvm pairs out of your flags and re-applies them to pass-diff via its own --mllvm. Anything that influences optimization through a channel other than the pipeline string, the module, or a cl::opt is not currently accounted for.

Compile stage

Three functions shell out to clang, all through run_cmd. All of them take the same flags list, which is the user's post--- argv, and write into the cfg-N folder.

FunctionDoes
run_cmd(argv, stderr) Runs an argv list via subprocess.run. Returns (output, None) on success, (None, stderr) on nonzero exit. Never shell=True — see the quoting note above. The stderr flag folds stderr into the returned output when true.
compile_to_ir(cpp, flags, ll_path) clang++ <flags> -fno-discard-value-names -Xclang -disable-llvm-passes -S -emit-llvm. The only call that parses C++. prepare_run passes the copy in src-N and adds -iquote <folder of the original> to the flags.
compile_to_asm(ll, flags, asm_path) clang++ -masm=intel <flags> -Wno-unused-command-line-argument -S file.ll. Feeds the "Final Assembly" panel.
extract_pipeline(ll, flags) clang++ <flags> -Wno-unused-command-line-argument -mllvm -print-pipeline-passes -S file.ll -o /dev/null. Returns the stripped pipeline string, or an error if clang printed nothing.

Starting the last two from the .ll skips the C++ frontend and gives the same assembly and the same pipeline as starting from the .cpp. C++-only flags (-I, -stdlib=, …) are unused for IR input, which clang warns about; the extra -W flag keeps a user's -Werror from turning that into a failure. The pipeline query cannot be merged into the IR step either: with -disable-llvm-passes clang prints only verify,verify,print and writes an empty .ll.

Run numbering

A run is addressed as (function, 1-based position in that function's list). Each list item stores its position in Qt.UserRole, and on_pass_selected passes the function and that number to show-diff. There is no text matching on pass names, so labels that repeat (a function pass runs many times per function) are no problem. Both subcommands count with the same tracker in pass-diff, so the numbers agree by construction — see PassRunTracker.

Diff rendering

The diff is computed in Python, not by pass-diff, which only ever emits two blobs of IR text.

build_side_by_side_diff(before, after) runs difflib.SequenceMatcher over the two line lists with autojunk=False — important, since autojunk heuristically discards lines that appear in more than 1% of a large input, which in IR means common instruction patterns. It walks the opcodes and returns two equal-length lists of (text, tag) pairs, inserting filler rows so that row i on the left always corresponds to row i on the right:

TagMeaningColor
equalUnchanged on both sidesnone
deleteLeft onlyred
insertRight onlygreen
replacePresent both sides, differinggreen (same as insert)
fillerPadding to hold alignmentdark gray

render_diff_lines(edit, lines) inserts one QTextBlock per row with a QTextBlockFormat background, so the highlight spans the full width rather than just the glyphs. Inserting through a cursor drags the viewport along, so it explicitly resets both scrollbars and the cursor to the top — otherwise a freshly selected pass would open mid-function.

link_scrollbars(a, b) cross-connects the two views' valueChanged signals in both directions, horizontally and vertically, which is what keeps aligned rows beside each other while you scroll. The mutual connection does not loop infinitely because Qt's setValue does not re-emit when the value is unchanged.

Both IR panels use a MarkerScrollBar, the same class that marks search hits in the pass list. diff_spans(lines) turns each run of consecutive colored rows into a (start, end, color) span in fractions of the row count, and the bar paints it on its groove, at least MARKER_HEIGHT pixels tall. Each panel marks its own colors: Old IR shows deleted and changed rows, New IR inserted and changed rows. The bars are always shown, so a diff that fits on screen still has its markers.

Demangling

The Demangle toolbar button (on by default) shows demangled C++ names in the assembly, the function dropdown and both IR panels. Not in the pass list, and not in the source.

  • MANGLED_NAME_RE = (?<![\w.])_Z[\w.$]+ finds Itanium names wherever they appear: @_Z…, %_Z…, $_Z… comdats and _Z…: asm labels, but not .L_Z…-style tokens. Clone suffixes such as .resume are part of the match; llvm-cxxfilt prints them as (.resume).
  • demangle_names sends all names not seen before to the llvm-cxxfilt next to CLANG in one call and caches the result. If the call fails, the tool is missing, or it returns a different number of lines, names are left as they are.
  • It is display only. The window keeps the raw texts (_asm_raw, _ir_raw, the dropdown's item data), so toggling just redraws, and pass-diff and the cache files always see mangled names. Demangled text is not valid IR any more (spaces, parentheses).
  • The IR is demangled before diffing, so the two sides line up on what is actually shown.

Startup sequence

main() parses the arguments (split at --; argparse rejects --output with --cache, and main rejects --code with --cache) and calls prepare_run, which bails out with a stderr message on any failure: pick pass-diff → ask it for its LLVM's tools folder and check clang++ exists there → select src-N / cfg-N → if complete, load the four files; otherwise compile IR → assembly → query the pipeline → run list-passes → write pipeline.txt and passes.txt. Only then is the QApplication constructed and the window shown. So the pass list is fully populated before the window appears, and a broken compile produces a terminal error instead of an empty UI.

Note QApplication(sys.argv[:1]) — Qt is given only the program name, so it cannot try to interpret our flags or clang's as its own.

Component: pass-diff

~500 lines of C++ in src/main.cpp. Built on LLVM's PassInstrumentationCallbacks — it does not scrape opt output.

Both subcommands use one callback class, PassRunTracker, registered on the instrumentation hooks; they differ only in which runs get snapshotted and what is printed. The pipeline is driven by runPipeline, which is plain new-pass-manager setup: four analysis managers, crossRegisterProxies, parsePassPipeline, MPM.run.

IR snapshots

Everything rests on turning an Any IR handed to a callback into comparable text. irSnapshot does this, deliberately mirroring LLVM's own StandardInstrumentations.cpp so the output lines up with what -print-changed would report.

irSnapshot(Any) renders the unit as text, and handles four unit kinds:

IR unitRendered as
Module *M.print()
Function *F.print()
LazyCallGraph::SCC *Each non-declaration function in the SCC, printed in order
Loop *printLoop()
Why the last two matter

Without explicit SCC and Loop cases, those units fall through to "". Then every CGSCC pass (InlinerPass, CoroSplitPass, ArgumentPromotionPass) and every Loop pass (LICM, LoopRotate, LoopFullUnroll) compares "" == "" and is reported as "did no changes" with empty IR — silently, for exactly the passes a user is most likely to be investigating. This was a real bug in an earlier iteration.

PassRunTracker

The pipeline runs function by function, so the runs are organised the way Compiler Explorer's Opt Pipeline view does it: every pass run is attributed to the function it ran on.

IR unitReported as
ModuleOne run under the pseudo function <Globals>, showing the whole module.
FunctionOne run under that function.
LazyCallGraph::SCCOne run per defined function of the SCC, each with only that function's IR. Functions the pass created (e.g. CoroSplitPass's .resume / .destroy) get a run with no before IR. After the pass, functions are looked up by name in the module, because the pass may have deleted one or moved it to another SCC.
LoopOne run under the loop's function, labelled <Pass> on loop %<name>, showing only the loop.

Three callbacks are registered:

  • BeforeNonSkippedPass — push a Frame with the runs this pass will report and their before snapshots.
  • AfterPass — pop, take the after snapshots, hand each run to the sink.
  • AfterPassInvalidated — pop and mark the runs invalidated. No IR is handed to this callback, so there is no after snapshot, but a pass that invalidated the unit it ran on changed it by any reading.
Why a stack and not a map

Keying before-snapshots by the IR unit's name looks natural and is wrong: passes rename the thing they run on. LoopRotatePass rewrites the loop header, which changes the loop's name, so the after-lookup misses and the pass silently produces no output — measured at 3 of 7 LoopRotatePass occurrences vanishing. CoroSplitPass has the same problem, adding .resume/.destroy functions to its SCC.

Passes nest properly, so a stack pairs before with after exactly. This is also why the AfterPassInvalidated callback must pop: miss it and the stack desynchronizes for every pass that follows. LLVM's own ChangeReporter is structured the same way.

The constructor takes two functions: Wants(unit) decides which runs get snapshotted, and Sink(run) receives each finished PassRun (Unit, Label, Before, After, Invalidated). A frame is pushed for every pass so the stack stays aligned with the after-callbacks, but runs that are not wanted carry empty strings.

list-passes & show-diff

list-passes wants every run and prints one line per run: Unit\tLabel\tdid changes if the run was invalidated or before and after differ, otherwise did no changes. The IR text is compared and discarded.

show-diff wants only the requested function, and counts that function's runs in the sink; the N-th one is printed with a header block (Pass :, Function:) and the two IR sections. An invalidated run prints (IR unit invalidated by the pass) as its after IR. That is the mechanism behind the laziness claim: show-diff walks the entire pipeline but serializes IR only for one function.

Because both subcommands number runs with the same tracker — including the invalidated ones and the ones created by a CGSCC pass — the N the UI reads from list-passes always addresses the same run in show-diff.

TargetMachine construction

createTargetMachineForModule(M) is short but carries the most design weight. It reads the triple from the module, looks it up in the TargetRegistry, and pulls default target-cpu / target-features from the first non-declaration function's attributes.

The deliberate choice is taking all of this from the IR rather than from our own command line. clang bakes the resolved triple into the module and the resolved target-cpu/target-features into each function's attributes, and TargetMachine::getSubtargetImpl(const Function &) re-reads those per function. So whatever -march, -mtune, or -m<feature> flags the user gave clang reach the cost models automatically, for any target, with zero flag translation on our side. The module-level CPU/features are only defaults for functions that happen to lack the attributes; per-function attributes still win.

Both failure modes — no triple in the module, or no registered target for the triple — print a warning to stderr and return nullptr, falling back to the target-agnostic cost model rather than aborting. Degraded but still useful.

main & argument parsing

toolchain-info is handled first: it prints LLVM_VERSION_STRING and the PASS_DIFF_LLVM_TOOLS_DIR that CMake defined from LLVM_TOOLS_BINARY_DIR, and exits. For the other two subcommands: hand-rolled argument scanning from argv[3] onward, recognizing --pipeline, repeated --mllvm, and — for show-diff — the first bare argument as the function and the second as the run index, which must be a positive number. Anything else is an error with usage. Then:

  1. InitializeAllTargetInfos/Targets/TargetMCs — required before any TargetRegistry lookup can succeed.
  2. If --mllvm options were given, synthesize an argv and call cl::ParseCommandLineOptions, which is what sets the global cl::opt values clang's -mllvm sets.
  3. parseIRFile, printing an SMDiagnostic and exiting on failure.
  4. Construct PassInstrumentationCallbacks, register StandardInstrumentations on it (with DebugLogging=false), then register a PassRunTracker configured for the subcommand.
  5. Print the # header lines and run the pipeline.

Exit status is 0 on success, 1 on bad arguments, unparseable IR, or a pipeline string parsePassPipeline rejects. A function name or run index that does not exist is not an error: the run is just never printed.

Linked LLVM components

From CMakeLists.txt: core, support, irreader, passes, analysis, transformutils, scalaropts, target, codegen, mc, plus AllTargetsInfos, AllTargetsDescs and AllTargetsCodeGens — all targets, so a TargetMachine can be built for whatever triple the module carries, which will matter once non-host targets come into play. If the LLVM was built as one shared library (LLVM_LINK_LLVM_DYLIB, as distribution packages are), pass-diff links that single LLVM library instead.

LLVM versions

Builds against LLVM 18 and newer. Since LLVM 21 the target triple is a Triple object where it used to be a string (Module::getTargetTriple, TargetRegistry::lookupTarget, Target::createTargetMachine), and printLoop takes a const Loop &. main.cpp handles both with #if LLVM_VERSION_MAJOR >= 21 and a const_cast. Tested with 18.1 and 23.0.0git.

Rough edges

Known and worth knowing before reading the code:

  • The first click on a pass re-runs the pipeline. Later clicks come from the diff cache. Fine at this scale; for large projects the first click is what stands in the way.
  • The pass list is eager. The first launch for a source and settings costs one full pipeline run before the window appears; only the per-pass IR is lazy. Later launches load it from the output folder.
  • Settings only change by restarting. Compiler flags and pass-diff are command-line only, and the Source panel is editable but inert: edits are never recompiled.
  • Headers are not versioned. Only the source file is copied into src-N; included headers are read from their original location, so a cfg-N computed before a header changed is still reused.
  • Switching function with a pass selected runs show-diff for run 2 of the new function and shows it although no row is selected; it also leaves that diff in the cache.
  • write_temp_file is unused. Kept for later; it writes into the current cfg-N.
  • Compilation errors exit to stderr rather than surfacing in the UI. The compile_to_ir/compile_to_asm error paths still carry TODO comments.
  • No source-line ↔ IR mapping, a prerequisite for the whole-project goal.
  • Diff colors are hardcoded dark-theme RGB values in LINE_COLORS, so they assume a dark Qt palette.
